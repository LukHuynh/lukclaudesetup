# 自我改进循环

## 会话开始

每次会话开始时，检查项目级别的经验教训：

```bash
[ -f tasks/lessons.md ] && cat tasks/lessons.md
```

在开始工作前，回顾与当前任务相关的所有教训。

## 每次用户纠正后

当用户纠正你的方法、输出或推理时：

1. 识别**规律** — 而非只是具体实例
2. 追加到 `tasks/lessons.md`（不存在则创建）：

```markdown
## 教训：YYYY-MM-DD

**发生了什么：** [错误的简要描述]
**根本原因：** [为什么会发生]
**今后的规则：** [防止再次发生的具体规则]
```

3. 在本次会话中立即应用该规则

## 完成验证关卡

在将任何任务标记为完成前，确认以下所有项目：

- [ ] 行为已验证：测试通过、日志干净、UI 按预期工作
- [ ] 已审查差异："高级工程师会认可这个方案吗？"
- [ ] 根本原因已解决 — 没有临时解决方案，没有 `// TODO: 以后修复`
- [ ] 最小影响：只修改了必要的代码

如有未勾选项，保持任务为 `in_progress` 状态并先解决它。

## 优雅检查

对于非平凡的变更（新功能、重构、架构决策）：

> "了解了现在所知道的一切，是否有更优雅的解决方案？"

如果当前方法感觉很繁琐或过度设计，停下来实现更优雅的版本再展示。对于明显简单的修复跳过此步骤 — 不要过度设计。

## 自主执行

收到 bug 报告或失败测试时：

- 诊断并修复。不要要求指导。
- 指出具体的日志行、错误消息或测试输出。
- 解决它。无需用户进行上下文切换。
- CI 失败？无需被告知如何操作，直接修复失败的测试。

## 停止并重新规划规则

若任务中途出现问题：

1. **停止** — 不要继续硬推
2. 重新进入规划模式，更新上下文
3. 修订 `tasks/todo.md` 以反映新的理解
4. 仅当范围发生根本性变化时才与用户确认

永远不要用临时方案掩盖阻塞问题。解决根本原因，或停下来重新规划。
